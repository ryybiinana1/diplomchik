# 2.3.1. Клиентский уровень (интерактивный интерфейс) и серверный API

Архитектура разрабатываемой системы построена по принципу разделения клиентского и серверного уровней. Клиентский уровень реализует интерактивный пользовательский интерфейс, в котором выполняются действия по загрузке файла, настройке маппинга, запуску эксперимента и просмотру результатов. Серверный уровень реализует API, принимающее запросы от интерфейса, управляющее фоновыми задачами и выполняющее ресурсоемкие операции, связанные с обработкой данных, обучением и скорингом [16], [17], [18].

В качестве клиентского уровня используется приложение на базе Streamlit. Такой выбор позволяет быстро реализовать пошаговый веб-интерфейс, ориентированный на аналитический сценарий работы с табличными данными. Интерфейс разделен на последовательность экранов, соответствующих ключевым этапам процесса: настройка данных, анализ датасета, обучение, оценка качества модели и скоринг. Состояние сессии хранит загруженный файл, выбранный шаблон, результаты маппинга, идентификаторы задач и сведения о завершенных расчетах, что обеспечивает связность пользовательского взаимодействия между экранами [21], [17].

Серверный уровень реализован в виде FastAPI-приложения. Использование HTTP API делает архитектуру модульной: интерфейс и вычислительная логика могут развиваться независимо, а взаимодействие между ними остается формализованным и воспроизводимым. На сервере выделены маршруты для проверки доступности приложения, получения описания контрактов данных, инспекции входного файла, создания и мониторинга задач обучения, получения результатов эксперимента, выбора доступных моделей и запуска скоринга новых данных [22], [23].

Разделение на UI и API дает несколько практических преимуществ. Во-первых, ресурсоемкие вычисления не блокируют работу пользовательского интерфейса и могут выполняться как фоновые задачи. Во-вторых, серверная часть получает централизованный контроль над валидацией входных данных, безопасностью файловых операций и сохранением артефактов. В-третьих, такой подход упрощает возможное расширение проекта: при необходимости API может использоваться не только текущим интерфейсом, но и другими клиентскими приложениями [16], [18], [37].

Взаимодействие между уровнями строится по запросно-ответной модели. Пользователь инициирует действие в интерфейсе, после чего соответствующий запрос передается в API вместе с файлом, настройками маппинга и параметрами эксперимента. Сервер принимает эти данные, создает идентификатор задачи и сохраняет промежуточное состояние обработки. Далее интерфейс периодически запрашивает статус выполнения и, после завершения операции, отображает результат в удобной для пользователя форме.

С архитектурной точки зрения клиентский и серверный уровни образуют внешний контур программной системы, а внутренний вычислительный контур представлен конвейером обработки данных, обучения и скоринга. Такое проектное решение соответствует поставленной задаче разработки self-service инструмента: пользователь получает простой пошаговый интерфейс, а все критические с точки зрения воспроизводимости и вычислительной корректности операции централизованно выполняются на серверной стороне.
