# 2.1.2. Нефункциональные требования: удобство интерфейса, повторяемость, безопасность путей и валидация входа

Нефункциональные требования определяют не перечень выполняемых системой операций, а те свойства, благодаря которым разработанное программное средство может рассматриваться как надежный и пригодный к практическому использованию инструмент. Для рассматриваемой задачи особое значение имеют удобство пользовательского взаимодействия, воспроизводимость результатов, защищенность операций с файлами и корректная валидация входных данных [16], [17], [37].

Требование удобства интерфейса обусловлено тем, что целевой пользователь системы не обязательно является разработчиком или специалистом по машинному обучению. Следовательно, работа с программным средством должна строиться как последовательность понятных этапов: загрузка данных, сопоставление колонок, предварительный анализ, обучение, оценка качества и скоринг. Интерфейс должен явно показывать текущее состояние процесса, предупреждать пользователя о недостающих шагах и предоставлять наглядный доступ к ключевым результатам без необходимости обращения к внутренним техническим деталям реализации [16], [17], [21].

Требование повторяемости связано с научной и прикладной надежностью получаемых результатов. Каждый запуск обучения или скоринга должен сопровождаться сохранением идентификатора задачи, параметров запуска, используемых файлов и выходных артефактов. Это необходимо для того, чтобы пользователь мог повторно обратиться к результату, сравнить несколько прогонов и обосновать, почему в качестве итоговой выбрана именно данная модель. Для дипломного проекта такое свойство особенно важно, поскольку оно демонстрирует, что система поддерживает не разовое вычисление, а управляемый эксперимент [19], [37], [39].

Отдельное требование относится к безопасности путей и изоляции файловых операций. Поскольку система принимает пользовательские файлы, сохраняет промежуточные результаты и позволяет выбирать модель для скоринга, необходимо исключить доступ к произвольным каталогам файловой системы. Допустимые пути должны разрешаться только внутри заранее определенных рабочих директорий, связанных с артефактами обучения и скоринга. Такое ограничение уменьшает риск несанкционированного обращения к посторонним файлам и соответствует базовым требованиям безопасной обработки данных в серверном приложении [31], [35], [36].

С валидацией входа связано следующее нефункциональное требование: система должна обнаруживать ошибки как можно раньше, до начала длительных вычислений. Для этого должны проверяться корректность структуры JSON-параметров, наличие обязательных полей маппинга, допустимость выбора колонок, соответствие шаблону входных данных, а также минимальная пригодность самого набора данных для дальнейшего анализа. Чем раньше обнаруживается ошибка, тем ниже вероятность получения ложного результата и тем выше качество взаимодействия пользователя с системой [23], [36], [38].

Важным требованием является и устойчивость к типовым проблемам исходных данных. Программное средство должно корректно работать с распространенным форматом кодировки CSV, обрабатывать пользовательские файлы без ручной преднастройки и формировать диагностические сообщения в тех случаях, когда набор данных не удовлетворяет необходимым ограничениям. Это делает систему пригодной для self-service использования, когда значительная часть предварительной технической подготовки должна быть перенесена с разработчика на сам инструмент.

Наконец, к числу нефункциональных требований относится понятность выходных результатов. Пользователь должен иметь возможность интерпретировать состояние задачи по статусу выполнения, видеть завершение этапов обработки и без затруднений переходить к скачиванию готовых артефактов. Таким образом, нефункциональные свойства разрабатываемой системы обеспечивают ее практическую состоятельность как программного средства поддержки решений по удержанию клиентов, а не как набора разрозненных вычислительных скриптов.
